# Turn a calibration migration into a technical talk

Read this when the migration includes a talk, slide outline or deck. Continue the user-selected outline, inspect its linked project evidence, and preserve speaker edits. Follow repository instructions for document locations and local commits; keep campaign decisions in the outline and reports. The talk should be aimed at someone who knows about ATLAS software, but not CorrectionLib, and perhaps doesn't know all the details of the tools or the corrections being applied. They will not understand short hand for optimizations made.

## Build the argument from evidence

Start with why this migration was worth trying, what constraints the original integration had to respect, and what benefits are being tested. Do not assume the new library helps merely because the migration runs. Establish the original tool's release, sample, resolved configuration, output and wall-time scope before showing replacement results. Name each implemented path and follow the executed call chain; do not present a proposal or an unused facade as working code.

Show enough of CorrectionLib's contract to orient the audience: typed/named inputs, correction data, evaluator, custom-node implementations and adapter plumbing. For paths B and C, show that physics executes through CorrectionLib nodes; distinguish historical implementations with external physics. A toy payload is a teaching illustration, not an ATLAS recommendation; check that it parses in the pinned evaluator and state its units, which a real-valued input type does not enforce. Label code fragments **actual code excerpt** or **simplified illustration**. State whether a displayed result is a corrected value, offset or scale. Do not suggest that a compiled C++ evaluator JIT-compiles each payload or that array bindings imply SIMD.

When practical use is one of the talk's questions, follow the toy with a small real analysis use case before diving into payload internals: show where the correction package is loaded, how semantic inputs map to concrete file leaves, how variations are evaluated, and where the corrected quantity is filled or saved for each state. Use lines from the executed runner, with source locations. If selected lines come from different parts of the file, label them as excerpts rather than one runnable block. Show one explicit leaf-name mapping on the main slide and put long field lists in backup. Do not invent an all-systematics facade when the actual runner composes a nominal facade with separate systematic or weight evaluators.

Separate the numerical case from the performance case. Explain the original-tool comparisons, covered systematic states, tolerance formula, exact identities/selections and missing observables. Do not say all original and replacement quantities are bitwise identical when the acceptance checks use numerical tolerances; later checkpoint-to-checkpoint parity may have a stricter byte-level result. A histogram overlay is a visual check, not per-object validation; a zero bin difference can hide small matched-object differences. Put full implementation hashes, input identity, method and caveats in notes or backup, with a compact source/checkpoint on each result slide.

Place the validation contract after the original tool's saved reference output is introduced and before the replacement results. A main-talk pT overlay can make agreement visible; a matched-object residual plot in backup can show `reference − candidate` against reference pT for representative alternatives. Match event identity, object counts and original indices before subtraction. State which state and display range the plots show, and whether a zoomed residual axis omits the tolerance envelope. Keep the full numerical acceptance over all objects and states as the actual pass criterion. Explain the absolute-plus-relative tolerance as a floor near zero plus a scale-dependent term, using the branch's native units. Do not invent a historical reason for a numerical coefficient when the scripts record only its value.

For timing, identify the timed workflow and what it includes: setup, imports, input preparation, recalibration, variations, comparisons, writing and CPU policy. Keep historical, newly repeated, nominal-only and full-systematics measurements distinct. Present improvements from the user's adapters and repeated work as such; do not attribute every gain or overhead to CorrectionLib's lookup evaluator. Carry unsuccessful and reverted experiments into backup when they explain the conclusion. End with measured benefits, costs, limits and a concrete next question.

Keep an early effort map simple when the talk will later unpack the benchmark: original reference → conversion and optimization → runnable framework and portable endpoints. Put each endpoint's time beside its box with its output scope; do not imply a common speedup scale when one job writes diagnostic trees and another writes a compact histogram. Move reader/I/O controls, matched nominal/full plot timings, and full timing-method detail to backup unless they are the main argument. When a nominal/full pair matters, rerun both with one harness and verify the nominal category agrees; label older nominal examples as historical if their input columns, chunking, output or CPU policy differed.

When the work includes a standalone wheel or one-command demo, make the input-to-output path visible in the talk: original data file, local package/script, state coverage and saved result. Put the exact reproducible command, archive/wheel size, output schema and cold/warm timing conditions in the report or backup; show the compact result on a main slide only when portability is one of the talk's questions. Separate fixture-based acceptance from the live-data demo, and do not compare its histogram-only time directly with a diagnostic run that reads references or writes per-object outputs. Read [portable demo packaging](portable-demo.md) for packaging and verification requirements.

Use one point per main slide. Let the on-slide content carry the claim and a few facts; put details in speaker notes and backup. Finish the content outline and evidence map while the speaker is still dictating the story. Build the deck from the settled outline, without treating a draft graphic or the outline's existence as approval of a visual theme, template or output destination. Preserve the speaker's direct wording where it conveys a substantive conclusion; avoid promotional phrasing.

## Make the outline a transferable deliverable

When the user plans to build the deck in another chat, write a self-contained outline in the requested repository/document location. Preserve the requested title and filename, even an unusual date, unless asked to change it. Include audience and provisional duration, the argument of each slide, suggested on-slide content, actual or illustrative code/config fragments, speaker notes and exact evidence links. Record unresolved measurements and scope distinctions explicitly. Verify local links and runnable teaching snippets; do not rely on conversation history being available to the deck builder. Preserve the user's edits and newer talk decisions when incorporating older discussion.

A useful starting sequence is motivation → CorrectionLib contract and example → original software/reference and read-only floor → real columnar use → shared framework integration → first comparison → optimization constraints and major changes → final comparison → backup. Adapt this to the latest speaker outline rather than forcing that order. Explain what standard CorrectionLib actually computes with a concrete compound such as sequential GSC, and show which stages remain in C++, inference or RNG libraries. Answer “what did CorrectionLib bring?” with that responsibility map and measured evidence, not only the use of JSON or a new build.

For a substantial optimization campaign, give the major mechanisms their own slides with a small before/after code example, checkpoint numbers and validation scope. Provide a single-page initial comparison and a single-page final comparison with all requested paths. Include the complete reduction history in backup from its original baseline, even if the main narrative starts at a later subcampaign. Smaller-impact changes also need concrete examples, not just names in a timing table. Preserve no-gain/reverted experiments and distinguish a CPU-policy change, rebuild control and fresh unchanged repeat from an implementation improvement.

Link reports, raw result summaries, source files, configuration snapshots and implementation commits. Name which evidence is historical, latest repeated, or a single integration run; do not let a filename such as “final profile” override its actual checkpoint. The handoff should tell the next chat what is implemented, what was proposed, and what still requires a measurement. Preparing this outline does not authorize building a deck when the user explicitly reserves that for a separate chat, nor does it authorize rerunning performance campaigns.

## Build and revise the editable deck

Use the speaker's requested scientific-talk skill/profile and presentation tools when available. Inspect their current instructions and disclose missing capabilities. Keep the deck beside the outline unless directed otherwise. Respect the user's artifact and Git scope for decks, assets, previews and backups.

Before each revision, inspect the current deck and preserve manual edits. Slide numbers refer to the user's current deck, not an older outline. Make a recoverable local copy before structural or format transformations. Keep an editable layout source and an explicit record of any export/postprocessing steps; do not regenerate from a stale outline over a newer deck.

For editable scientific decks:

- Use native PowerPoint bullet/numbered paragraphs, with hanging indents so wrapped lines align with the first line's text. Typing a bullet glyph or number into ordinary text does not satisfy this requirement.
- Use native equations for mathematical expressions, including subscripts, powers, absolute values and tolerances. Keep literal code as code. Unicode lookalikes alone are not equation mode.
- Center bottom captions and reference rows that refer to the whole slide. Keep code left-aligned and place object-specific annotations with their object.
- Use small readable text hyperlinks for sources and code, never a figure as the link. Keep evidence accessible without obscuring the claim.
- Verify the title-page affiliation and use authentic organizational logos with preserved proportions.

Inspect rendered slides after edits, including code indentation, wrapped lists, tables, captions and links. Verify native list/equation structure in the saved file as well as its appearance. A successful export is not visual verification in the target application. If a tool cannot preserve native equations, retain an editable source and validate any export workaround. State when target-application rendering remains unverified; a layout-only preview is insufficient.

## Explain the executable path and the demo

Include a call-path/data-flow diagram in backup when the implementation spans adapters, inference, RNG and CorrectionLib. Start with the user's real top-level correction call. Show nominal, systematic and selection/weight entry points separately if the caller invokes them separately; do not turn a nominal-only call into an imaginary all-in-one pipeline. Follow each through bindings, CorrectionLib nodes and native classes to payloads and numerical-library dependencies. Distinguish call arrows from data passed back through the caller, and show where payload loading happens. For paths B and C, show NN and RNG calculations behind nodes. If inspected code still runs physics from an application or wrapper, report the boundary and incomplete migration status; distinguish it from historical implementations.

An analysis demonstration should teach the requested analysis. Show imports, construction/loading, the input helper's role, iteration over variations and an indented histogram fill. If a wrapper constructs a differently named native class, explain that mapping and identify the actual JSON-loading constructor. Label a shortened adaptation honestly and identify any omitted helper; do not call it standalone runnable code. Remove validation-only bookkeeping such as lists of observed state names, comparisons and diagnostic recording helpers from a histogram-only example. Preserve them in the acceptance harness. State whether the histogram includes selections or weights, and whether weight-only variations change its plotted quantity. Check snippet syntax and control-flow indentation without rerunning the physics campaign solely for a slide edit.

Use audience-facing terms with explicit counts. Replace unexplained “coverage” with what was checked: expected systematic names, outputs, objects/events, or tested phase-space boundaries. Distinguish nominal plus kinematic systematic configurations from additional weight-only systematic variations; counts of configurations are not automatically counts of independent nuisance parameters. Define the reference, sign of the difference, absolute/relative tolerances and their units in the mathematical acceptance statement.

Report benchmark hardware with CPU model, physical/logical cores as relevant, host memory, OS or virtualization layer, and guest-visible memory when using WSL/VMs. Distinguish machine capacity from CPU affinity/worker policy used in a particular run, and installed RAM from measured peak memory. A later hardware inventory must not silently imply that every historical run used the same CPU policy.

For extracted calibration size, measure the actual runtime files and label compression and units (MB versus MiB). Separate compressed CorrectionLib JSON, manifests/model dependencies, uncompressed data, wheels/libraries, input events and loaded memory. Name the implementation path: an experimental graph payload is not the hybrid path's payload. Preserve differing historical sizes with their revision/measurement context rather than silently overwriting them.

## Publish evidence only within the authorized scope

Before an authorized source publication, inspect tracked files, packed Git history and the working directory separately. A large build/results tree does not predict the upload size. Check host limits and large tracked blobs, preserve commits needed for the talk's optimization history, and exclude build products, input data and presentation assets according to the user's scope. A new repository containing copied source/history is not automatically a hosting-service fork; report the actual relationship. Confirm visibility when it is unspecified and matters to audience access. Do not infer permission to publish from a request to add citations.

If authentication requires a temporary checkout or bare copy on another host, use it only for the authorized publication, verify the remote revision, then remove the specific temporary copy after checking its location. Preserve the authoritative checkout. Avoid leaving a second large source tree behind.

Link code excerpts to immutable source revisions and line ranges, and timing changes to the commits that implemented them. Verify that the cited code matches the slide and that checkpoint commits are present in the published history. Keep local reports distinct from public evidence: a local path is not an audience-accessible URL. If the user elects to omit unpublished references, remove those links without deleting the reports or fabricating public replacements. Check for leftover local hyperlinks in saved document relationships as well as visible labels. Publication does not itself validate a scientific claim.
