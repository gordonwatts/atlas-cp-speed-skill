# Convert calibrations to CorrectionLib

Use the same original PHYSLITE file for all three paths. **A** runs unmodified release AnalysisBase. **B** runs the replacement in AnalysisBase with the existing analysis configuration. **C** reads the original file with uproot and runs the columnar workflow in Python.

B and C use the same CorrectionLib node implementations and payload configuration for the same numerical prescription. All calibration, systematics, selection and weight calculations enter through CorrectionLib nodes, which may call shared C++ or numerical libraries. Adapters handle data and statuses. Keep Awkward array handling and histogramming in Python. Validate each faithful replacement independently against A.

## Lead the conversion and delegate coding

The campaign lead is the high-end model responsible for architecture, sequencing, acceptance criteria, end-to-end source review and interpretation of profiles. It may ask a peer of comparable capability to review architectural choices.

The lead scopes implementation, build, validation, profiling and benchmark work for a subagent on the most capable available Sol model (currently `gpt-6.2-sol`) at high reasoning. In Codex, pass explicit `model` and `reasoning_effort: "high"` overrides and `fork_turns: "none"` to `spawn_agent`. Include the repository and skill paths, authoritative checkout, any accepted checkpoint, fresh results directory for runs, user decisions and exclusions, eligible prior evidence, design or measurement question, edit scope, evidence to return, and stop or escalation conditions. Wait for the worker to finish or raise a decision, review the returned changes and evidence, and log the decision before follow-up.

A worker given a scoped assignment uses this skill to execute that assignment. It returns results and routine fixes to the named lead and escalates architecture or acceptance decisions there. Campaign-level delegation belongs to the lead. Use one runtime owner and keep calibration and benchmarking to one CPU and one execution thread unless the user requests otherwise.

## Conversion workflow

1. **Set scope and resolve ownership.** Read the repository working agreement. Determine whether this is a fresh campaign or a continuation. Resolve the authoritative checkout from the owner handoff, pin the AnalysisBase release, toolchain and [CorrectionLib develop](https://github.com/gordonwatts/correctionlib/tree/develop) revision, and choose fresh result storage. Run authoritative builds and numerical work in WSL `atlas_al9`. Keep reports, talk assets and inspection copies in the Windows repository. Determine eligibility for prior code, evidence and results before the [reuse inventory](references/efficient-campaigns.md#reuse-inventory-before-implementation). Respect any independent-derivation boundary before consulting archived campaign results. Freeze the input, object collections, working points, state coverage, public interfaces, acceptance checks and timing/output contract. Record the deliverables and [completion evidence for the assignment](references/efficient-campaigns.md#match-completion-evidence-to-the-assignment) at intake. Keep a chronological task log and living [optimization register](references/efficient-campaigns.md#collect-and-transfer-optimization-ideas).
2. **Capture the independent reference and measure A.** Use [AnalysisBase discovery](references/analysisbase-discovery.md) and [ATLAS numerical guidance](references/atlas-lessons.md) to trace the initialized tools, resolver, source data and actual systematic states. Freeze the original controls and validate the observer on a small real sample before recording required per-object identities, values, stages and statuses. Use the observer output for acceptance. Measure the [read control, nominal and full-systematics workloads](references/validation-and-timing.md#measure-the-physlite-to-histogram-workflow) with the declared timing boundaries. The 10× aspiration is the sum of A's calibration-to-ntuple and ntuple-to-histogram wall times divided by C's direct PHYSLITE-to-file wall time for the same full-systematics pT histogram.
3. **Design, build and validate a faithful checkpoint.** Start with the original tool boundaries. Before porting each numerical body, identify existing routines and callers, use a supported schema node when faithful, and reuse callable source implementations where practical. Register any required extension behind CorrectionLib. Build a reproducible offline exporter, verify dependency closure and track source-to-payload provenance. Use the [graph and payload design procedure](references/graph-design.md) and [independent acceptance checks](references/validation-and-timing.md#independent-authority). Preserve the original recipe, precision, edge cases, errors, statuses and stream. Freeze a validated, timed B/C baseline before optimization. Required numerical failures keep that checkpoint experimental. When standalone delivery is in scope, smoke-test its loading and execution on a small real input as soon as an initial stage works.
4. **Review the execution path and implement obvious architectural savings.** The lead traces the actual B/C call graph and data flow across tools, outputs and systematic states. Use coarse baseline phase times and targeted call, traversal or copy counts to estimate how much wall time a candidate could remove. If those measures leave a specific question unresolved, use a short diagnostic profile of the faithful baseline. Delegate clear structural simplifications such as dropping a whole intermediate copy or repeated preparation. Validate and time each before commissioning detailed profiling. Follow [architectural experiments](references/validation-and-timing.md#explore-and-benchmark-architectural-refactors).
5. **Profile the simplified workflow and address architecture.** Have Sol collect [representative profiles](references/profiling.md#recommended-sequence) with phase/tool elapsed times, process CPU time, native stacks below tool level and supported hardware counters. The lead identifies the callers and workflow decisions driving those costs and commissions a trial of the strongest viable structural candidate. When combining tools saves work, compose independently callable routines shared with separate tool workflows, and exercise both paths. Record why credible untried candidates were deferred and reprofile after material changes.
6. **Tune remaining hotspots.** Reconsider the whole workflow at each candidate. Use the [bounded loop and common techniques](references/efficient-campaigns.md#bound-the-optimization-loop), including optional native multiple outputs and array processing when evidence supports them. Test one mechanism at a time. A short diagnostic can discard a clearly unpromising trial after focused semantic checks. Retained changes require full applicable acceptance and matched production timings. When local gains flatten, revisit the architecture for a larger opportunity. The campaign may stop after ten consecutive measured attempts each improve end-to-end C by at most 0.5%, or when no concrete, evidence-backed opportunity remains in scope. Inconclusive or diagnostic results leave the count unchanged. Keep matched same-stream C timings for gains attributed to engineering changes.
7. **Package, measure and document the result.** For the standalone deliverable, build and test the [ROOT-free CPython 3.14 wheel and visible PEP 723 script](references/portable-demo.md) in isolation. If ROOT supplies randomness, experimental benchmarks are authorized to use versioned Philox4x32-10 with double-precision Box–Muller after preserving the faithful checkpoint. Apply [changed-stream acceptance](references/validation-and-timing.md#intentional-random-stream-changes). Freeze and verify the loaded provider, payload and stream for each delivered runtime. For final framework timing, apply the [20% Path B budget](references/validation-and-timing.md#apply-the-path-b-framework-budget) to the final B variant. For final standalone timing, measure the delivered C workflow. Link acceptance for each measured variant. For a full campaign, retain phase/tool times and within-tool CPU costs in the [supporting profiling study](references/report-and-talk-guide.md#required-profiling-study-in-the-supporting-evidence), including a final native profile with at least 60 seconds of actual standalone processing. Follow the [report and talk guide](references/report-and-talk-guide.md), including its [standard opening table for total A/B/C workflow times](references/report-and-talk-guide.md#opening-timing-table-template). Put adopted optimizations and measured outcomes in the main report, account for the contents of every delivered wheel, and show the executed A/B configuration, tested C command and verified complete C script. A full report includes the input read footprint and 20 ranked remaining ideas, with links to agreement plots for every calibrated variable. Before delivering a report, run the [independent report review](references/report-and-talk-guide.md#independent-report-review) with GPT-6.2 Sol at low reasoning and address its confirmed findings. Deliver the reproducible commands, frozen configuration, provenance, machine-readable results and optimization record required by the assignment. Preserve completed milestones with descriptive local commits.

If a general evaluator defect or optimization surfaces, check current upstream source and existing issues or PRs, and prepare a minimal independent reproduction with revision, expected and observed behavior, regression evidence and tradeoffs. Follow repository authorization rules for publication and pushes. For skill edits based on campaign lessons, use the [contribution guide](references/contributing.md).
